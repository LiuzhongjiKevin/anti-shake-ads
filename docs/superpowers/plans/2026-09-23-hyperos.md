# HyperOS onboarding and persistent status

> Execute inline with executing-plans; existing user authorization covers repository updates and test releases.

**Goal:** A single prominent protection button, guided HyperOS setup and visible background controls.
**Architecture:** Keep the existing return engine. A pure Java state resolver drives home/notification copy; a specialUse foreground service exposes status and pause/stop actions. System authorization remains user controlled.
**Tech Stack:** Android Java, SDK 35, min 26, platform views, GitHub Actions emulator.
**Spec:** The current user request and the decisions below.

## Design and constraints

- Homepage: app name, large round enable button, short live status, two small entries (protected apps/settings). No dashboard clutter.
- Palette: porcelain #F5F6F2, forest #174B40, ink #17332C, muted #586B62, pale green #E3EDE5, white #FFFFFF. Native sans with distinct weights; system font scaling respected. Return arrow/shield is the product's identifying mark.
- Setup follows selected apps → accessibility → optional notifications and battery/OEM settings. Returning from Settings refreshes facts without repeatedly reopening permissions. The next required step is shown by the main button.
- No root, silent permission grants, fake VPN, wake locks, periodic alarms, networking, or accessibility auto-clicking system toggles.
- OEM autostart and task-lock status cannot be read reliably; always label manual checks. Deep links are best effort with fallbacks.
- Off stops foreground service; pause remains visible; missing accessibility never claims protection is ready. Android may still kill or restrict the process.
- Preserve app choices and advanced return policy. No changes to the heuristic engine.

## Review focus

1. User cancels any authorization: no settings loop or false ready state.
2. User stops protection: sticky service/boot cannot turn it back on.
3. Accessibility disconnects: notification and home say repair required.
4. OEM activity missing/not exported: system details fallback, no crash.
5. Notification permission denied: protection can work, visible warning and settings route remain.

## Ledger

- Ruling: Run cloud builds because local SDK/network is unavailable. Use isolated local snapshot and atomic GitHub tree commit; preserve unrelated remote files.
- Ruling: Permission setup is guided, not silent. Standard Android APIs require the user's explicit approval.
- Ruling: Foreground service is for user-visible session status and controls, not a promise of permanent residency.
