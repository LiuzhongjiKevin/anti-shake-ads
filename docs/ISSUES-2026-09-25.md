# 2026-09-25 小米真机反馈：未解决

## 原始反馈

- 多个应用的开屏/摇动广告在当前应用内打开类似浏览器的网页，而非切换到其他应用。
- 包子漫画 → 应用商店：日志显示「未恢复：已达到返回上限」，3 次，1585 ms。用户只感到一次返回，怀疑目标尚未完成打开就触发。

## 已确认的代码问题

- GuardEngine.update 对相同来源包名直接返回 NONE，没有同包页面识别；不能处理同应用广告落地页。
- 检测到目标包后立即返回 BACK；首次动作没有目标页面稳定等待。
- 后续最短450 ms重试，第三次后再等450 ms即失败；这与约1.5秒内耗尽预算相容，但不能证明该真机的唯一根因。
- back() 在控制器复核窗口和调用系统接口之前增加 attempts；控制器忽略 performGlobalAction 的 boolean 结果。
- 因此3次是引擎发出的动作次数，不是3次已确认完成的页面返回。
- 现有1500 ms WindowReadiness仅处理应用窗口暂缺，不处理有包名但仍处启动/跳转动画的窗口。

## 下一步验证要求

1. 取得小米型号、HyperOS/Android版本、包子漫画与应用商店版本，以及失败录屏；确认页面稳定后手动返回一次/多次的效果。
2. 真机诊断分别记录目标首次出现、窗口变化、动作实际调用时间、系统布尔结果、返回后包名/窗口，不保存页面正文、账号或输入内容。
3. 用启动过渡/首次不接收返回的模拟目标验证，避免仅用立即响应Back的固定测试页。
4. 根据窗口稳定情况安排首次返回和后续确认；不能只提高次数。系统接受动作与确实恢复来源应分开记录。
5. 同应用网页需要页面层识别及原页面恢复验证；不能把所有 WebView 当广告，否则会关闭正常登录、文章或支付页面。确认实际界面后决定通用信号和逐应用规则。

## 2026-10-29 核心状态机修改（未上真机）

- 跨应用：检测到跳转后不再立即返回，等目标页面（包名 + Activity）稳定 400 ms，或最多等 1500 ms 再动作。每次重试前等待核实（返回后 700 ms，重新打开后 900 ms），并等页面再次稳定。
- 开启“重新打开来源”时，顺序改为 返回 → 重新打开来源 → 返回。
- 同应用广告页：新增 `AdPageClassifier`，按广告 SDK 落地页 Activity 类名加用户自定义规则识别，在保护应用内用返回关闭。内置类名尚未在小米真机上确认。
- 保护时间窗只限制何时检测跨应用跳转；已开始的恢复最多持续 6 秒。
- 核心测试：43 项引擎测试、15 项分类器检查全部通过。
- 控制器已接上：从窗口状态事件中取 Activity 类名（经 PackageManager 确认是 Activity），每次动作前清掉来源和目标的旧类名。自定义规则存放在 `ad_rules`，暂时没有设置界面。
- 尚未完成：`Prefs` 中“重新打开来源”仍默认关闭。没有构建 APK，也没有在真机上验证。
